1. WHY THE ENVIRONMENT SETUP WAS PROMPTING FOR 10 VARIABLES (RESOLVED)
----------------------------------------------------------------------
- Root Cause:
  The AI Studio Secrets / Environment Setup UI scans `.env.example` and prompts
  you for every **uncommented** `KEY=VALUE` line. Because all 10 variables were
  previously uncommented in `.env.example`, the platform prompted you to fill
  them in manually.
- Fix Applied:
  All lines in `.env.example` are now commented out (`# ...`). The Android app
  reads its Firebase configuration directly from `app/google-services.json` and
  `app/src/main/res/values/firebase_applet_config.xml` and does NOT require any
  manual `.env` entries to compile or connect to Firebase Cloud Firestore.

2. POSTGRESQL & `DATABASE_URL` REMOVAL VERIFICATION
---------------------------------------------------
- PostgreSQL, SQLite server databases, `psycopg2`, `SQLAlchemy`, and
  `DATABASE_URL` have been completely removed from `backend/main.py`,
  `backend/requirements.txt`, and the Android codebase.
- `DATABASE_URL` is **NOT** referenced or required anywhere at build time or
  runtime. All persistent server and client data uses **Firebase Cloud
  Firestore**.

6. EMAIL + PASSWORD + 6-DIGIT EMAIL OTP LOGIN (USERS & SUPER ADMIN)
-------------------------------------------------------------------
A) Super Admin Account (`hj195345@gmail.com`):
   - **Super Admin Email**: `hj195345@gmail.com` (`username: "hj123"`, `role: "SUPER_ADMIN"`).
   - **No Hardcoded Plaintext Passwords**: Plaintext passwords and OTP secrets are
     never stored in source code, Firestore documents, `.env.example`, or
     `firebaseStep.txt`.
   - **Setting or Updating Super Admin Password**:
     1. On the Login screen, tap **Admin Console** -> **Set / Reset Admin Password?**
        (or use **System Configuration -> Admin Account Settings -> Rotate Password**
        when already signed in).
     2. Enter `hj195345@gmail.com` and tap **Send 6-Digit OTP**.
     3. Verify the 6-digit OTP within 60 seconds and enter your chosen password
        (minimum 8 characters, at least 1 number and 1 special character). The
        password is hashed with salted SHA-256 / PBKDF2-HMAC-SHA256.
     4. Duplicate admin accounts are prevented; existing Super Admin records are
        updated in-place.

B) Login Flows (2-Step Email + Password + 6-Digit Email OTP):
   - **Admin Login Flow**:
     1. Switch to **Admin Console** on `LoginScreen`, enter `hj195345@gmail.com`
        and password, and tap **VERIFY & SEND ADMIN OTP**.
     2. Credentials and `SUPER_ADMIN` / `ADMIN` role eligibility are validated
        first. Invalid credentials return a generic `"Invalid email or password."`
        error.
     3. A 6-digit verification OTP is issued to `hj195345@gmail.com` and the app
        navigates to `OtpScreen`. Access to `AdminPanelScreen` is strictly
        blocked until OTP verification succeeds (`session.otpVerified == true`).
     4. After OTP verification, an HMAC-signed `SUPER_ADMIN` session is created
        and `AdminPanelScreen` opens.
   - **Normal User Login Flow**:
     1. In **User Login** mode, enter user email and password and tap
        **LOGIN WITH EMAIL OTP**.
     2. After password verification, a 6-digit OTP is sent to the user's
        registered email address.
     3. Access to protected user screens (`WelcomeScreen` / `DashboardScreen`) is
        granted only after the 6-digit OTP is verified.
     4. **Continue with Google** (via Jetpack `CredentialManager` +
        `FirebaseAuth.signInWithCredential(GoogleAuthProvider.getCredential(idToken, null))`)
        is preserved on both Login and Sign Up screens.
   - **User Registration Flow**:
     1. Self-registration (`SignUpScreen`) enforces duplicate email/username
        checks and hard-locks `role = "USER"` so no client-side input can
        self-assign `SUPER_ADMIN` or `ADMIN`.
     2. After registration, a 6-digit `SIGNUP_VERIFY` OTP is issued to verify
        email ownership before opening the user session.

C) Email OTP Security & Rate-Limiting Settings:
   - `OTP_TTL_SECONDS = 60`: Every 6-digit OTP expires strictly `60` seconds
     after `issuedAtMillis`. The Android `OtpScreen` displays a live `00:60`
     countdown synchronized with `expiresAtMillis`.
   - `OTP_MAX_SENDS = 3` & `OTP_WINDOW_SECONDS = 600`: Maximum `3` OTP emails per
     normalized email address within any rolling `10-minute` (`600` seconds)
     window, enforced atomically via thread-safe locks (`_otp_lock` in Python and
     `synchronized(otpMutex)` in Kotlin).
   - **Single-Use & Invalidation on Resend**:
     * Each OTP can be verified only once (`consumed = true` immediately upon use).
     * Requesting or resending a new OTP immediately invalidates any previous
       unconsumed OTP for that email (`invalidated = true`).
     * Stored OTP records (`otp_challenges` collection) persist only salted
       SHA-256 / HMAC-SHA256 digests (`otpHash` + `salt`), never plaintext OTPs.

D) Firestore Schema & Security Rules (`firestore.rules`):
   - `isVerifiedBootstrappedAdmin()` in `firestore.rules` authorizes
     `hj195345@gmail.com` when `request.auth.token.email_verified == true`.
   - `otp_challenges` is registered in `PROTECTED_SYSTEM_COLLECTIONS` so
     server-side OTP hashes and rate-limit counters cannot be tampered with by
     client CRUD operations.
   - Normal users can read/write only their own profile (`users/{uid}`) with
     `role == 'USER'` and `status == 'ACTIVE'`, and cannot escalate roles.

E) Multi-Provider Email OTP Delivery Configuration (`backend/main.py`):
   - **Root Cause & Fix of Exposed / Default OTP Issue**:
     Previously, `backend/main.py` returned `"testOtpCode"` in JSON responses and
     `AdminRepository.kt` populated `devPreviewCode` on `OtpChallengeState`, which
     `OtpScreen` displayed on screen. That has been completely removed:
     * Neither `backend/main.py` nor `AdminRepository.kt` ever generates a
       default/hardcoded OTP (`"000000"`) or returns OTP values in API responses,
       DTOs, console logs, or UI screens.
     * Every OTP is generated via `secrets.randbelow(900000) + 100000` (Python)
       or `java.security.SecureRandom` (Kotlin) and stored exclusively as a
       salted SHA-256 / HMAC-SHA256 digest (`otpHash` + `salt`) with 60s expiry,
       15s resend cooldown, max 5 verification attempts, and max 3 sends per 600s
       rolling window.
     * Upon successful password verification, the UI displays:
       `"OTP sent to your registered email (<masked_email>)."`
   - **Email Service Providers Supported (`_deliver_otp_email` in `backend/main.py`)**:
     Configure any one of the following providers via server-side environment
     variables (never hardcode secrets in source code or `firebaseStep.txt`):
     1. **Resend API**:
        * `RESEND_API_KEY` (server-side API key from Resend)
        * `EMAIL_FROM` (verified sender address, e.g., `no-reply@yourdomain.com`)
     2. **SendGrid API**:
        * `SENDGRID_API_KEY` (server-side API key from SendGrid)
        * `EMAIL_FROM` (verified sender address)
     3. **SMTP (STARTTLS)**:
        * `SMTP_HOST` (e.g., `smtp.gmail.com`)
        * `SMTP_PORT` (default `587` with STARTTLS)
        * `SMTP_USER` (sender email address)
        * `SMTP_PASSWORD` (app password / SMTP secret from Secret Manager)
        * `SMTP_FROM` (optional sender header)

F) Google Login (OAuth / Credential Manager) & Account Linking:
   - Android uses Jetpack `CredentialManager` (`GetSignInWithGoogleOption`) +
     `FirebaseAuth.signInWithCredential(GoogleAuthProvider.getCredential(idToken, null))`
     and `AdminRepository.authenticateWithGoogle(...)` (mirrored on the backend
     by `POST /api/v1/auth/google`).
   - Accounts are matched and linked by normalized verified email:
     * Existing `"EMAIL"` accounts are linked to `"EMAIL,GOOGLE"` without creating
       duplicate user records or escalating roles.
     * New Google users are created with `role = "USER"`, `status = "ACTIVE"`, and
       `authProvider = "GOOGLE"`.
     * `BLOCKED`, `SUSPENDED`, `INACTIVE`, or `DELETED` accounts are rejected.
     * Google-verified logins establish an authenticated session directly without
       an unnecessary second email OTP challenge.

     * Total registered users

     * Currently active users (active sessions + `ACTIVE` accounts)

       `SUSPENDED`, `INACTIVE`), authentication provider (`EMAIL`, `GOOGLE`,

     * Supports search, status/role/provider filters (`ALL`, `ADMINS`, `ACTIVE`,
       `SUSPENDED`, `BLOCKED`, `INACTIVE`, `GOOGLE`), sorting (`NEWEST`,
       `LAST_LOGIN`, `MOST_LOGINS`, `NAME`), and pagination (`Prev` / `Next`).
     * Supports **Block / Unblock**, **Activate / Deactivate**, **Role Assignment**,
       and **Individual Permission Overrides (`customPermissions`)**.
   - **RBAC Roles & Last Super Admin Safeguard**:
     * Supported roles: `SUPER_ADMIN`, `ADMIN`, `DATA_MANAGER`, `EDITOR`,
       `SUPPORT_AGENT`, `ANALYST`, `VIEWER`, `USER`, `BLOCKED`.
     * Blocking, suspending, deactivating, demoting, or deleting the last active

H) UI Navbar Spacing Root Cause & Fix:
   - **Root Cause**: `MainActivity.kt` wraps `AppNavigation(modifier = Modifier.padding(innerPadding))`
     inside a root `Scaffold`, which already applies status-bar top padding and
     navigation-bar bottom padding. Child screens were applying `.systemBarsPadding()`,
     `.statusBarsPadding()`, or nested `Scaffold` / `TopAppBar` default `windowInsets`
     a second time, creating extra blank space above the top navbar.
   - **Fix Applied**: Set `contentWindowInsets = WindowInsets(0, 0, 0, 0)` and
     `windowInsets = WindowInsets(0, 0, 0, 0)` on nested `Scaffold`s and
     `TopAppBar`s, removed redundant `.systemBarsPadding()` / `.statusBarsPadding()`
     on child screens, and reduced oversized top `Spacer`s so the navbar aligns
     cleanly with the top of every screen.
